## 0. Architectural Pushbacks

Before presenting the architecture, I need to challenge five assumptions in your current plan. These are not style preferences — they are structural problems that will cost you a rewrite if not addressed now.

### Pushback 1: The Reporting Agent's Output Is Not Ready for Intelligence

I examined the actual cleaned Excel your Reporting Agent produces (`report-whatsapp-clevertap-2026-07-14.xlsx`). It has critical problems:

- **70% of dates are NULL.** 14 out of 20 rows have no Date, Week, or Month. Your Timing Intelligence section is impossible with this data.
- **The dates that DID parse are wrong.** Campaign `HFRP_WA_ResortBillZero_03052026` (May 3, 2026) was parsed as `2026-03-05` (March 5, 2026). The Reporting Agent confused day/month format.
- **Percentages are strings** ("1.25%", "51.12%") instead of numeric values. The Intelligence Engine would have to re-parse every metric.
- **It outputs per-channel files.** The file I received contains only WhatsApp (20 rows). But your Intelligence Report needs cross-channel comparison (WhatsApp vs Push vs RCS). Where does the Intelligence Engine get the other channels?

**My recommendation:** Define a strict **Data Contract** between the Reporting Agent and Intelligence Engine (Section 6 below). The Intelligence Engine should reject files that fail contract validation, and the Reporting Agent should be updated to meet the contract. Do NOT build defensive parsing in the Intelligence Engine to compensate for Reporting Agent bugs — that creates two systems both trying to clean data, which is exactly the duplication you said you want to avoid.

### Pushback 2: Per-Channel Export Breaks Cross-Channel Intelligence

Your Reporting Agent UI shows channel selection (Step 2: "Channels to Clean") and exports one channel at a time. But the most valuable insights in your April report are cross-channel:

- "Push outperforms WhatsApp on CTR (1.20% vs 0.77%)"
- "Push delivers 132 influenced conversions vs WA's 109 with half the campaigns"
- "Shift primary channel from WhatsApp to Push"

If the Intelligence Engine receives only WhatsApp data, it cannot produce these insights. You have two options:

**Option A (Recommended):** The Reporting Agent exports ALL channels in one file. The Intelligence Engine receives the complete dataset and handles channel segmentation internally.

**Option B:** The Intelligence Engine accepts multiple per-channel files and merges them. This is more complex, error-prone (what if the user forgets to upload Push?), and creates a worse UX ("upload file 1... now upload file 2... now upload file 3").

I strongly recommend Option A. The Reporting Agent should clean all channels and produce one unified export. Channel filtering for export purposes can still exist as a separate "Export" feature, but the Intelligence Engine should always receive the full dataset.

### Pushback 3: The LLM Should NOT Receive the Excel File Directly

Your vision says: "The LLM should receive... The cleaned Excel file generated by the Reporting Agent."

This is dangerous. Here's why:

- A 36-row Excel with 25 columns and full message bodies is ~15,000 tokens. For larger datasets (100+ campaigns), this explodes.
- LLMs cannot reliably compute weighted averages, group-bys, or rankings from raw tabular data. They hallucinate numbers.
- The April report contains exact statistics (CTR 1.20%, CTOR 2.40%, 132 conversions). If the LLM computes these, some will be wrong and you won't know which.

**The correct architecture (which you already designed in the earlier chat):** Deterministic code computes ALL numbers and produces a `facts.json`. The LLM receives facts.json (pre-computed, verified numbers) plus the business/vertical profile, and narrates from those facts. It classifies message text (tone, opening style) but never calculates a metric.

The one exception: the LLM should receive the raw **message text** for creative intelligence (tone analysis, opening line classification, CTA assessment). But it receives this alongside pre-computed performance metrics for those messages — it interprets the text, it does not compute the numbers.

### Pushback 4: "Business Profile Once, Never Again" Is Too Rigid

Your onboarding vision is form-based: user fills fields once, stored permanently. But the most valuable intelligence in your Claude chat came from iterative corrections:

- "Meta 50% delivery is observed, not a restriction" (a correction)
- "Push uses Total Viewed, not Delivered" (a data quirk)
- "No revenue tracking for pre-paid members" (a business rule)
- "Urgency only works within 72 hours" (a learned pattern)

These are not things a user can fill in a form on day one. They emerge during analysis. The architecture must support:

1. **Structured onboarding** (the form — captures identity, verticals, KPIs)
2. **Progressive enrichment** (the system detects gaps and asks, or the user corrects)
3. **Learned observations** (patterns discovered from data that become permanent knowledge)

The Business Profile should be a **living document** with a structured core (form-filled) and an observations layer (accumulated over time). Not a static config.

### Pushback 5: "Template Designer" Is the Wrong Mental Model

You said this module is currently called "Template Designer" and you plan to rename it. Good — because the name implies it *creates* templates. Your product *analyzes* them.

But beyond naming: the current UI shows it as a sibling to "CleverTap Agent" and "MoEngage Agent" in the Agents sidebar. This positioning implies it's another data-processing agent. It is not. It is a fundamentally different kind of module:

- The Reporting Agents are **ETL tools** (transform data from format A to format B)
- The Intelligence Engine is an **analytical product** (consume data, produce insights)

These should not be peers in a sidebar. The Intelligence Engine should be the *destination* after data preparation — a separate workspace with its own navigation, state, and context. Think of it as: Reporting Agent = the kitchen (prep), Intelligence Engine = the restaurant (delivery).

**Recommended name:** "CRM Intelligence" or "Campaign Intelligence" — not "Analytics" (too generic) or "Template Designer" (wrong metaphor).

### 1.2 Separation of Concerns

| Layer | Responsibility | Owns |
|-------|---------------|------|
| Reporting Agent | Data extraction, cleaning, normalization, format standardization | Column mapping, platform quirks, file parsing |
| Data Contract | Schema validation, type enforcement, completeness checks | The interface spec between the two systems |
| Intelligence Engine | Analytics, classification, pattern detection, narration, rendering | Business logic, KPI formulas, aggregation, LLM orchestration |
| Persistence | Storage, retrieval, versioning | Profiles, runs, facts, reports, observations |

### 1.3 What the Intelligence Engine Does NOT Do

- Does NOT re-clean data (that's the Reporting Agent's job)
- Does NOT parse platform-specific column names (abstracted by the contract)
- Does NOT store raw campaign files (the Reporting Agent owns those)
- Does NOT compute metrics the LLM could hallucinate (all math is deterministic code)
- Does NOT present a dashboard as primary output (it produces a report document)

### 3.2 LLM Usage Summary

| Point | Purpose | Input | Output | Fallback |
|-------|---------|-------|--------|----------|
| L1 (Phase 4) | Classify messages | Campaign texts + taxonomy enums | Structured tags per campaign | Rule-based keyword matching |
| L2 (Phase 5) | Narrate insights | facts.json + profile + messages | Structured report sections | Factual template-based prose |

**Total LLM calls per analysis: 2** (not counting retries). Both are structured-output calls with strict schemas. Both have deterministic fallbacks. The pipeline never hard-fails due to LLM unavailability.

### 3.3 What Makes This Different From a ChatGPT Wrapper

| Aspect | ChatGPT-style | This Architecture |
|--------|---------------|-------------------|
| Numbers | LLM computes from raw data (unreliable) | Code computes, LLM reads (verified) |
| Consistency | Different answer each run | Same facts.json every run; narrative varies only in phrasing |
| Auditability | "The AI said 1.2% CTR" (who checks?) | facts.json is independently verifiable |
| Scalability | Token limit at ~100 campaigns | Aggregation handles 10,000 campaigns; LLM sees only summaries |
| Reproducibility | Non-deterministic | Classification cached by message hash; facts are deterministic |

### 4.2 Key Design Decisions

**Why Organization → Business Profile is 1:1 (not 1:N):**
An organization IS a business. Multi-business support means multiple organizations, each with their own login. Trying to model "one user manages multiple businesses" creates UX complexity (constant switching) that isn't worth it for V1. A consulting firm managing multiple clients should have separate org accounts.

**Why Vertical is a separate entity (not embedded in Profile):**
Because runs are tied to verticals. When you generate a report, it's "HFRP May 2026" — the vertical is the analytical context. Keeping it as a first-class entity enables: filtering runs by vertical, loading vertical-specific KPI definitions, and comparing the same vertical across months.

**Why Observations are separate from Profile:**
Because they accumulate over time, have provenance (which run discovered them), and can be unconfirmed (pending user approval). They're a changelog of learned knowledge, not a static field.

**Why Facts are stored as JSONB (not normalized tables):**
Because the facts schema evolves as we add new aggregation dimensions. A rigid relational schema for facts would require migrations every time we add "by_headline_quality" or "by_cta_strength." JSONB gives us schema flexibility while still being queryable for trend comparison.

### 4.3 Storage for Future Features

| Future Feature | What it reads | Already modeled? |
|----------------|---------------|-----------------|
| Historical trends | Facts table (compare run N vs N-1) | Yes |
| Chat with reports | Report.insights_json + Facts.facts_json | Yes |
| Campaign recommendations | Observations + Facts (patterns that worked) | Yes |
| Multi-user | Organization table (add users table) | Extensible |
| A/B test tracking | Extend Run with test_group flag | Extensible |

## 6. Data Contract (Between Reporting Agent and Intelligence Engine)

This is the most critical interface in the system. If this is wrong, everything downstream breaks.

### 6.1 Required Columns

| Column | Type | Required | Notes |
|--------|------|----------|-------|
| Date | date (YYYY-MM-DD) | YES | Must be fully populated. No nulls. |
| Time | time (HH:MM:SS) | YES | 24-hour format. |
| Week | integer | NO | Nice to have; engine can compute from Date. |
| Month | string | NO | Nice to have; engine can compute from Date. |
| Campaign Name | string | YES | Must follow convention: `{VERTICAL}_{CHANNEL}_{OFFER}_{DATECODE}` |
| Channel | string | YES | Standardized: "WhatsApp", "Push Notification", "RCS", "Email", "SMS" |
| Segment | string | YES | Free text; engine classifies. |
| Estimated Reach | integer | NO | Used for error rate if present. |
| Total Sent | integer | YES | |
| Total Delivered | integer | YES | For Push: this should be Impressions/Viewed (Reporting Agent's job to map). |
| Total Viewed | integer | YES | |
| Clicked | integer | YES | |
| Click Through Conversion | integer | YES | |
| Influenced Conversion | integer | YES | |
| Message | string | YES | Full message body. Critical for creative intelligence. |

### 6.2 Type Rules

- All count columns MUST be integers (not strings, not floats)
- Date MUST be ISO format (YYYY-MM-DD), fully populated
- Time MUST be HH:MM:SS format
- Percentage columns are OPTIONAL (engine computes them from counts)
- Message MUST be non-null (campaigns without message text cannot be analyzed for creative intelligence)

### 6.3 Structural Rules

- The file MUST contain ALL channels in a single export (not per-channel)
- Minimum 5 campaigns (below this, aggregations are statistically meaningless)
- No duplicate rows (same campaign name + same date + same segment = duplicate)

### 6.4 What Happens When the Contract is Violated

The Intelligence Engine does NOT silently fix problems. It returns a clear rejection:

```
CONTRACT VIOLATION: Cannot proceed with analysis.

Issues found:
  1. Date column has 14 null values (70% of rows).
     → Return to Reporting Agent and fix date parsing.
  
  2. CTR column contains string values ("1.25%").
     → This column is optional. Engine will recompute from Clicked/Sent.
     → But Date nulls are blocking.

  3. Only 1 channel present (WhatsApp).
     → Cross-channel analysis impossible.
     → Re-export from Reporting Agent with all channels included,
        OR proceed with single-channel analysis (limited insights).
        [Proceed anyway]  [Go back]
```

### 6.5 Why This Contract Matters

Without it, the Intelligence Engine becomes a second data-cleaning system. You said "I don't want to duplicate logic." The contract is how you enforce that. The Reporting Agent's job is to produce data that meets this contract. The Intelligence Engine's job is to assume the data is clean and focus entirely on analysis. If the contract is violated, the answer is "fix the Reporting Agent," not "make the Intelligence Engine more defensive."

## 8. Risk Assessment

| Risk | Severity | Mitigation |
|------|----------|------------|
| Reporting Agent output doesn't meet contract | HIGH | Define contract first. Build contract validator. Don't ship Intelligence Engine until Reporting Agent meets it. |
| LLM hallucinates numbers | HIGH | LLM never computes. facts.json is the single source of truth. Every number in the report traces back to deterministic code. |
| User abandons onboarding | MEDIUM | Make Step 3 optional. Let the system work with just company name + vertical. Enrich over time. |
| Report quality feels generic | MEDIUM | The system prompt must inject deep domain context (brand voice, industry norms, vertical objectives). Not just "you are a CRM analyst" — but "you understand vacation ownership, pre-paid membership models, referral psychology." |
| Small datasets (5-10 campaigns) produce weak insights | MEDIUM | Set minimum thresholds per aggregation dimension. If < 3 campaigns per group, don't report that dimension. Flag to user: "Not enough data for timing analysis." |
| Taxonomy drift (new offer types appear) | LOW | The classifier flags unknowns. The observation system proposes additions. The taxonomy grows organically. |

## 10. Architecture Decision Records

### ADR-1: Intelligence Engine validates but does not clean

**Decision:** If data violates the contract, reject with actionable error. Do not attempt to fix.
**Rationale:** Two cleaning systems = bugs, inconsistency, blame ambiguity. One system cleans (Reporting Agent). One system analyzes (Intelligence Engine). The contract is the boundary.

### ADR-2: All numbers computed by code, never by LLM

**Decision:** The LLM receives pre-computed facts and generates prose. It never performs arithmetic.
**Rationale:** LLMs reliably hallucinate when asked to compute weighted averages over 36 rows. A single wrong number in an executive report destroys trust permanently.

### ADR-3: LLM output is structured JSON, not free-form markdown

**Decision:** Both LLM calls (classify + narrate) output strict JSON schemas. The renderer converts JSON → DOCX.
**Rationale:** Structured output enables: (a) retry on schema violation, (b) mixing LLM prose with code-generated tables in the same document, (c) partial rendering if one section fails, (d) future features (chat, search) that need parsed sections.

### ADR-4: One unified export, all channels

**Decision:** The Intelligence Engine expects a single file containing all channels.
**Rationale:** The most valuable insights are cross-channel. Per-channel files make cross-channel analysis impossible and create user burden (multiple uploads). The Reporting Agent should be modified to support unified export.

### ADR-5: Business Profile is form + observations (not form-only)

**Decision:** Structured onboarding captures identity/verticals. Observations accumulate from analysis runs.
**Rationale:** The most valuable business knowledge emerges during use, not during setup. "Meta 50% is a pattern" and "urgency only works within 72 hours" cannot be known before the first analysis.

## Summary

The CRM Intelligence Engine is an analytical product that sits downstream of data preparation. Its value comes from three things done exceptionally well:

1. **Deterministic analytics** — every number is computed by code, verified, and traceable.
2. **Contextual intelligence** — the LLM understands this specific business, this vertical, this audience, and writes accordingly.
3. **Professional output** — the report feels like it was written by a senior CRM consultant who spent a week with the data, not by a chatbot that processed a prompt.

The architecture ensures this by separating concerns cleanly: the Reporting Agent owns data quality, the Data Contract enforces the boundary, the Intelligence Engine owns analysis and insight generation, and the LLM is used surgically — only for text classification and narrative writing, never for computation.
